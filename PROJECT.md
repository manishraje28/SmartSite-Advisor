# SmartSite Advisor — Project Documentation

> Generated by reading the actual source code (backend, frontend, and the Python scoring engine) as of the current state of the repository. This is a description of what is genuinely implemented and working, including known gaps and inconsistencies — not a marketing summary.

## 1. What This Project Is

SmartSite Advisor is a real-estate platform for the Mumbai / Thane / Navi Mumbai market with three cooperating systems:

1. **Node.js/Express backend** — REST API, MongoDB persistence, live web scraping, and a swarm of Groq-LLM-powered advisory agents.
2. **Python/Flask scoring microservice** — a deterministic, formula-based property scoring engine (not an LLM) that the backend calls after every property is created or re-synced.
3. **React (Vite) frontend** — buyer and seller web experiences: search, AI matchmaking, side-by-side comparison, property listing/management, and seller analytics.

There is no monorepo tooling — `backend/`, `frontend/`, and `scoring-engine/` are three independently run projects with their own dependencies.

## 2. Tech Stack

**Backend** (`backend/`, Node.js, CommonJS)
- Express **5.2** (Express 5, not 4), Mongoose **9.4** (MongoDB ODM), JWT (`jsonwebtoken`), `bcryptjs` for password hashing
- `axios`, `cheerio` — HTTP/HTML parsing
- `crawlee` **3.18** + `playwright` **1.62** — headless-browser web scraping (MagicBricks)
- `groq-sdk` — LLM calls for the AI agent swarm
- `node-cron` — scheduled daily re-scrape job
- `helmet`, `cors`, `morgan` — security headers, CORS, request logging
- `mongodb-memory-server` (dev) — in-memory MongoDB fallback if Atlas is unreachable
- `@googlemaps/google-maps-services-js` is listed as a dependency but **is not actually used** — `nearbyAmenitiesService.js` calls the Google Places/Distance Matrix REST APIs directly via raw `axios`

**Scoring Engine** (`scoring-engine/`, Python)
- Flask **2.3** + `flask-cors` — a tiny REST API (`POST /score`, `GET /health`)
- Pure Python, no ML/AI libraries — this is a hand-authored weighted-formula scorer, not a trained model

**Frontend** (`frontend/`, React 19, Vite 8)
- React **19.2**, `react-router-dom` **7**, Vite **8**
- Tailwind CSS **4** (new `@import "tailwindcss"` syntax) with a custom `ai-indigo`/`ai-emerald`/`ai-purple` color namespace
- `framer-motion` — animation throughout
- `leaflet` + `react-leaflet` — interactive maps (property markers, POI pins)
- `recharts` — radar charts, area charts (seller analytics, score breakdowns)
- `lucide-react` — icon set
- `@react-google-maps/api` — present as a dependency, not confirmed wired into any live page beyond `nearbyAmenitiesService` on the backend side

## 3. Architecture

```
┌────────────────────┐        ┌──────────────────────┐        ┌───────────────────────┐
│   React Frontend    │──────▶│   Express Backend      │──────▶│  Python Scoring Engine  │
│   (Vite, port 3000)  │  REST │   (port 5000)           │ HTTP  │  (Flask, port 5001)     │
└────────────────────┘        │                        │       └───────────────────────┘
                               │  ├─ MongoDB Atlas       │
                               │  ├─ Groq LLM API        │  (AI agent swarm)
                               │  ├─ OpenWeatherMap API  │  (environment/AQI scoring)
                               │  ├─ Google Places API   │  (nearby amenities, optional)
                               │  └─ MagicBricks.com     │  (live scraping via Playwright)
                               └────────────────────────┘
```

- The backend **auto-spawns the Python scoring engine as a child process on startup** (`backend/src/jobs/scoringEngineProcess.js`) if it isn't already running — tries `PYTHON_EXECUTABLE` env var, then `python`, then `python3`, then a hardcoded dev-machine fallback path. This means `node server.js` alone brings up the whole scoring pipeline; no manual second terminal is required.
- A **daily cron job** (`backend/src/jobs/autoSyncJob.js`, `node-cron`, runs at midnight) re-scrapes Mumbai/Thane/Navi Mumbai from MagicBricks and syncs new/changed listings into MongoDB, sequentially per city with a re-entrancy guard.
- On a **fully empty database**, `backend/src/utils/autoSeed.js` seeds 13 static sample properties (correctly labeled `verifiedLive: false` — they are not real scraped data) so the app isn't blank on first run.

## 4. Data Models (MongoDB / Mongoose)

### `User`
Single schema for both buyers and sellers, discriminated by `role`.
- `name`, `email` (unique, validated), `password` (bcrypt-hashed, `select: false`), `phone`, `role` (`buyer` \| `seller` \| `admin`, default `buyer`), `avatar`, `isVerified`, `isActive`, `lastLogin`
- `passwordResetToken`/`passwordResetExpires` fields exist but no reset-password flow currently uses them
- Password hashing happens in a `pre('save')` hook; `comparePassword()` instance method wraps `bcrypt.compare`
- `toJSON` transform strips `password` and reset-token fields automatically

### `Property`
The core entity. Notable fields beyond the obvious (`title`, `description`, `propertyType`, `listingType`, `price`, `location`, `specifications`, `images`, `status`):
- `amenities`: a **fixed enum of 19 values** (`Lift, Gym, Swimming Pool, Parking, Security, Power Backup, Garden, Clubhouse, CCTV, Intercom, Rainwater Harvesting, Solar Panels, Children Play Area, Jogging Track, Tennis Court, Basketball Court, Gas Pipeline, Water Storage, Maintenance Staff`) — any value outside this list fails validation
- `aiScore`: `{overall, locationScore, connectivityScore, amenitiesScore, roiPotential, lastScoredAt}` — written by the Python scoring engine
- `environmentScore`: `{overall, aqi, aqiLabel, airQualityScore, pollutantExposureScore, comfortScore, trendScore, trendLabel, summary, recommendations[], pollutants, weather, forecast, source, lastUpdated}` — written by the OpenWeatherMap integration
- `sourcePortal`, `sourceUrl`, `verifiedLive` — **default to `null`/`null`/`false`** (deliberately — see §9). Only the real scraper sets these to genuine values; a manually-listed property is honestly unverified until proven otherwise.
- Geospatial (`2dsphere`) index on `location.coordinates`, a weighted text index on `title`+`description`, and several compound indexes for common buyer-search filter combinations
- Virtual `formattedPrice` (₹X.XX Cr / ₹X.XX L / plain number)

### `BuyerPreferences`
One per buyer (unique on `user`). Drives personalized matchmaking.
- `preferredPropertyTypes`, `listingPreference`, `budget {min,max}`, `preferredLocations`, `maxDistanceKm`, `referencePoint` (GeoJSON), `minBedrooms`, `minCarpetAreaSqFt`, `furnishingPreference`, `requiredAmenities`, `buyerSegment`
- `weights`: `{price, location, amenities, connectivity, roiPotential}` — the personalization formula's coefficients, must sum to 1.0 (validated server-side), default `{0.35, 0.30, 0.20, 0.10, 0.05}`
- `savedProperties[]`, `viewedProperties[]`

### `SellerInsights`
One per property (unique on `property`), AI-generated/backend-computed, seller-facing.
- `currentScore` (mirrors `Property.aiScore`), `scoreHistory[]`
- `demandStats` (`views/saves/inquiries` + weekly trend), `demandLevel`
- `buyerSegmentMatch` (probability 0-100 per segment: family/investor/student/bachelor/retiree), `topTargetSegment`
- `improvementSuggestions[]` — each has its own `_id`, `type`, `priority`, `message`, `impact`, `isResolved`/`resolvedAt`
- `marketComparison`, `optimalPriceRange`, `rentVsSellRecommendation`

## 5. The AI Scoring System (Python microservice)

This is the deterministic, non-LLM part of the "AI" — a weighted-formula engine (`scoring-engine/`), called by the backend after every property create/re-sync.

**Composite formula** (`engines/composite_scorer.py`):
```
overall = locationScore × 0.35 + connectivityScore × 0.30 + amenitiesScore × 0.20 + roiScore × 0.15
```

**Sub-scores:**
- **Location** (`location_scorer.py`, 0-100): area popularity, infrastructure quality, safety, growth potential, nearby amenities — looked up from a hand-authored knowledge base (`config.py`) keyed by **locality** (Bandra, Juhu, Worli, Kharghar, Vashi, etc.), not by city, because city-level data doesn't differentiate between an ultra-luxury and an affordable neighborhood in the same city.
- **Connectivity** (`connectivity_scorer.py`, 0-100): metro/bus proximity, highway access, business-hub distance, airport time, from the same locality-keyed knowledge base.
- **Amenities** (`amenities_scorer.py`, 0-100): required amenities (Parking/Security/Gym/Power Backup/Lift, 40pts), luxury amenities (Swimming Pool/Clubhouse/Tennis Court/Basketball Court/Solar Panels, 30pts), outdoor spaces (Garden/Jogging Track/Children Play Area, 20pts), and a modernization bonus based on property age (10pts). The amenity label strings are matched **exactly against the Property schema's enum**, so this stays accurate as amenities data changes.
- **ROI Potential** (`roi_scorer.py`, 0-100): rental yield (from the same per-locality knowledge base, calibrated to realistic Indian gross yields of ~1.5-4%), appreciation potential, market liquidity (days-to-sell), and a small demand-trend bonus from view-count vs. area average.

**Locality resolution** (`resolve_area_key()` in `config.py`): tries to find a known locality name inside the property's address string first (so "Juhu Tara Road, Juhu, Mumbai" resolves to the real Juhu entry), falls back to a city-level entry (Mumbai/Thane/Navi Mumbai), then to a generic `Default` bucket only as a last resort.

**Backend integration** (`backend/src/services/scoringService.js` + `propertyService.js`):
- `scoringPropertyAsync(property)` runs **non-blocking**, in parallel, alongside `openWeatherService.getEnvironmentalInsights(property)` for the AQI/environment score, right after a property is saved.
- If the Python engine is unreachable, scoring fails silently (logged, not thrown) and the property just stays unscored until the next successful attempt — there is no retry queue.
- `scoringValidator.js` checks the property has valid location/coordinates/price/amenities/specifications before attempting to score it.

**Environment/AQI scoring** (`backend/src/services/openWeatherService.js`): calls OpenWeatherMap's current weather, air pollution, and air pollution forecast endpoints in parallel, computes a weighted 0-100 `overall` from air quality (35%), pollutant exposure (20%), weather comfort (25%), and a 24h AQI trend (20%). Results are cached in-memory per coordinate for 30 minutes. Returns `null` (no fabricated fallback) if `OPENWEATHERMAP_API_KEY` is missing or the API call fails.

## 6. Live Data Pipeline (Web Scraping)

**Source**: MagicBricks.com is the only one of the three original target portals (Housing.com, 99acres, MagicBricks) that actually serves content to a headless browser — Housing.com and 99acres both return outright anti-bot blocks (HTTP 406 / 403) even on a plain page load, so they are not scraped.

**`backend/src/agents/scrapers/magicBricksScraper.js`** (Crawlee + Playwright):
- Paginates through MagicBricks search results (`&page=N`, ~30 listings/page) up to a configurable `maxPages` (default 10), stopping early if a page comes back empty.
- Deduplicates listings across pages (MagicBricks repeats some "featured" listings) by `sourceUrl`, falling back to `title+price` when no link is captured.
- Parses each card's title into bedrooms/project name/locality/city, price text (`₹10.13 Cr` → rupee integer), and carpet area.
- **Amenities**: since amenities aren't on the search-results page, it does a second crawl pass (concurrency 3) visiting each listing's own detail page and reading its full amenities list, then maps MagicBricks' free-text labels ("Kids play area", "Reserved Parking") onto the Property schema's fixed enum — unmappable labels are dropped rather than saved.

**`backend/src/agents/PortalSyncManager.js`**:
- `harvestAndSyncRegion({city, locality, limit, maxPages})` — runs the scraper, then upserts each listing: matches existing properties by `sourceUrl` or `title+city`, tracks price changes into `priceHistory`, and routes every new or price-changed property through the **real** scoring pipeline (`scoringPropertyAsync`) rather than fabricating scores.
- `forceSinglePropertySync(propertyId)` — only marks a property `verifiedLive: true` if it genuinely has a `sourceUrl` from a real scrape; otherwise returns an honest failure message instead of rubber-stamping an unscraped listing.

**Fallback behavior**: if a live scrape genuinely returns nothing, `RealEstateScraperAgent` falls back to a small static sample corpus — but marks it `verifiedLive: false` rather than pretending it's live data.

## 7. AI Agent Swarm (Groq LLM)

`backend/src/agents/groqClient.js` provides `callGroqAgent({systemPrompt, userPrompt, temperature, maxTokens})`, trying models in order (`qwen/qwen3.8-27b`, then `groq/compound-mini`) and falling back to a hardcoded static response if every model fails or returns unparsable JSON.

| Agent | File | Purpose | Output |
|---|---|---|---|
| **Parichay** | `ParichayAgent.js` | Buyer profiling from free-text ("I want a 2BHK near good schools with clean air") | `personaCategory`, `roiWeight`/`transitWeight`/`amenitiesWeight`/`ecoHealthWeight`, `suggestedBudget`, `plainEnglishSummary`, `recommendedSearchQuery` |
| **Valuation & ROI** | `ValuationROIAgent.js` | LLM-estimated fair-value/appreciation/rental-yield narrative for one property | `valuationScore`, `fairMarketStatus`, `projected5YrAppreciation`, `estimatedMonthlyRent`, `rentalYield`, pros/risks |
| **GeoSpatial** | `GeoSpatialAgent.js` | LLM-imagined commute/AQI narrative (does **not** call the real Google Places or OpenWeatherMap integrations — purely LLM-generated plausible numbers) | `geoScore`, `aqiIndex`, commute estimates to metro/school/hospital/IT park, neighborhood verdict |
| **Negotiation** | `NegotiationAgent.js` | EMI/counter-offer strategy | recommended counter-offer, EMI, down payment, tax savings, step-by-step negotiation script |
| **Constructor Upgrade** | `ConstructorUpgradeAgent.js` | Seller-facing "what should I upgrade to raise my score/price" plan | current vs. potential score, prioritized upgrade list with cost estimate and ROI multiplier per upgrade |
| **Debate Orchestrator** | `AgentDebateOrchestrator.js` | Simulates a 3-agent panel debate comparing 2+ properties, producing a consensus winner | multi-round debate transcript + `consensusWinner` with score and reasoning |

**Where these actually appear in the UI:**
- **Parichay** → `ParichayVoiceAssistant`, a floating chat button mounted globally on every page (with optional voice input via the Web Speech API) — not tied to any specific route.
- **Constructor Upgrade** → embedded directly in the Seller Dashboard as `ConstructorUpgradeWidget`.
- **Negotiation** → a modal (`NegotiationAdvisorModal`) opened from the Property Details page.
- **Valuation & GeoSpatial** → called by the backend `/api/agents/*` endpoints but not currently wired into a dedicated frontend widget beyond what other pages request ad hoc.
- **Debate Orchestrator** → the endpoint and backend logic exist and work, but the frontend widget that displayed it (`AgentDebateWidget`) was **removed from the Comparison page** per an explicit product decision earlier in this project's development — the component file still exists but is unused.

## 8. Buyer-Facing Features

- **Registration/Onboarding**: sign up → buyers land on `/buyer/onboarding`, a form that sets property type/location/budget preferences **and** interactive priority sliders (Price Fit / Location / Amenities / Connectivity / ROI Potential) that map directly onto the `BuyerPreferences.weights` used by the matching formula — moving one slider proportionally redistributes the rest so they always sum to 100%. Pre-fills from existing preferences on revisit; reachable later via an "Edit Preferences" link in the Buyer Hub.
- **Buyer Hub / Matchmaking** (`/buyer/dashboard`): personalized property feed. `matchmakingService.calculateMatchForProperty()` computes a 0-100 match percentage per property as a weighted sum of price-fit + the property's location/amenities/connectivity/ROI sub-scores, using the buyer's own weights, plus small bonuses for matching preferred locations/property types and a penalty for missing required amenities. Only shows **verified, real (scraped)** properties — the static unverified sample corpus is explicitly excluded from these results. Supports "Load More" pagination against the full dataset (not capped at one page), smart-tag quick filters (clean air, budget, high ROI, by city), and grid/list/map view modes.
- **Properties / Search** (`/properties`, `/buyer/search`): full listing browse with search (by title/city/address, natural-language spec matching like "3bhk", "clean air", "luxury"), property-type filter, sort (score/price), and grid/map view. Paginated with a real "Load More" reflecting the true total count from the API.
- **Comparison** (`/buyer/compare`): pick 2-4 properties from a picker grid that includes a **server-backed search bar** (debounced, queries the full ~350-property dataset directly rather than only whatever page happened to be loaded), then view a side-by-side plain-English comparison: price/EMI, pros/cons, AQI, an interactive map + AI chatbot per property (`ExplainerChatbot` — ask about nearby malls/schools/hospitals/metro and see them pinned on the map, auto-fitting the viewport to include every pin), and a radar-chart/table comparison view.
- **Property Details** (`/property/:id`): full property page with AI compatibility score, AI valuation summary, negotiation strategy modal, the map+chatbot widget, and a downloadable/printable "AI Audit Report" modal.
- **Saved properties**: `POST /api/properties/:id/save` increments a save counter; `BuyerPreferences.savedProperties[]` exists in the schema but no dedicated "My Saved Properties" page currently renders it (the route exists as a stale placeholder in an unused routing file — see §10).

## 9. Seller-Facing Features

- **Create Property** (`/seller/properties/create`): 5-step wizard (Basics → Location → Details → Amenities → Pricing) covering every `Property` schema field. **Known gap**: submitted coordinates are currently hardcoded to Bangalore (`[77.5946, 12.9716]`) regardless of the entered address — there's no geocoding step — and images are a single hardcoded placeholder path (no upload UI).
- **Seller Dashboard** (`/seller/dashboard`): polls insights/analytics every 5 seconds. Shows aggregate stats (avg AI score, total views/saves/inquiries), a weekly engagement trend chart, a property list with per-property `ScoreRing`, a radar chart of the selected property's sub-scores, a read-only AI-suggestions panel, a buyer-segment-match breakdown, and the embedded Constructor Upgrade widget.
- **Seller Insights API** (`/api/seller/*`): paginated insights list, single-property insight detail, an analytics rollup (total views/saves/inquiries, average score, conversion rate), and a resolve-suggestion endpoint. **Known gap**: the resolve-suggestion UI (`SuggestionItem`/`InsightCard` components) exists in the codebase but is not actually rendered by the live Seller Dashboard — the dashboard shows suggestions read-only, with no way to mark one resolved from the UI (the backend endpoint works; nothing currently calls it).

## 10. Known Architectural Inconsistencies

Documented honestly since the request was for what's actually implemented, warts included:

- **Duplicate authentication systems**: `/api/auth/*` (self-contained, issues a JWT with `{id, role}`, auto-creates `BuyerPreferences` on buyer registration) and `/api/users/*` (layered controller/service, JWT payload is just `{id}`, no auto-preferences) both exist and both work, but behave subtly differently. The frontend only uses `/api/auth/*`.
- **No authentication middleware anywhere in the backend.** JWTs are issued at login, but no route actually verifies one except a manual inline check in `GET /api/auth/me`. Every other "protected" concept (which seller owns a property, which buyer's preferences to load) is enforced purely by trusting a plain `sellerId`/`buyerId` passed in the request — there is no `req.user` derived from a verified token guarding any endpoint.
- **CORS is wide open** (`origin: '*'`) — the code comment notes this was "temporary while resolving a VPN routing issue."
- **Inconsistent API response envelopes** — some controllers use a shared `sendSuccess`/`sendError` helper (`{success, message, data}`), while `authRoutes.js`, the inline `buyerRoutes.js` handlers, and `agentController.js` each hand-roll their own response shape.
- **Two parallel frontend routing definitions**: `frontend/src/routes/index.jsx` (a data-router-style config with no actual `ProtectedRoute` enforcement) is dead code — `App.jsx` defines and mounts all routes actually in effect directly. Some UI links (in `Footer.jsx`/`Sidebar.jsx`) point at routes (`/seller/analytics`, `/buyer/recommendations`, `/buyer/saved`) that only exist in the unused routing file and 404 in the live app.
- **A legacy component library and design spec are orphaned**: `frontend/src/components/common/*` (Button, Card, Input, Badge, Modal, Pagination) and `frontend/src/design-system.js` describe an earlier beige/yellow/orange color scheme and aren't used by any live page — the actual app is built from hand-written utility classes in `index.css` plus the indigo/emerald `ai-*` Tailwind palette.
- **`GeoSpatialAgent`'s output is LLM-imagined**, not computed from the real `nearbyAmenitiesService` (Google Places) or `openWeatherService` (OpenWeatherMap) integrations, even though both exist and work elsewhere in the codebase.

## 11. Environment Variables (backend `.env`)

| Variable | Purpose |
|---|---|
| `PORT`, `NODE_ENV` | Server port and environment |
| `MONGO_URI` | MongoDB Atlas connection string (no database name in the URI defaults to a database literally named `test`) |
| `JWT_SECRET`, `JWT_EXPIRES_IN` | Auth token signing |
| `CLIENT_ORIGIN` | Intended CORS origin (currently overridden by wildcard, see §10) |
| `SCORING_ENGINE_URL` | Python scoring engine base URL (default `http://localhost:5001`) |
| `PYTHON_EXECUTABLE` | Optional override for which Python binary to auto-spawn the scoring engine with |
| `OPENWEATHERMAP_API_KEY` | Environment/AQI scoring — silently disabled if absent |
| `GROQ_API_KEY` | Required for every AI agent (Parichay, Valuation, GeoSpatial, Negotiation, Constructor Upgrade, Debate) |
| `GOOGLE_MAPS_API_KEY` | Required for `nearbyAmenitiesService` (real nearby-amenities enrichment); returns `null` gracefully if absent |

## 12. Running the Project

```bash
# Backend (auto-starts the Python scoring engine and the daily sync cron)
cd backend && npm install && npm run dev

# Frontend
cd frontend && npm install && npm run dev
```

The scoring engine can also be started manually for debugging: `python scoring-engine/app.py` (port 5001).
